# 质量与测试

## 1. TDD 流程

新增行为或修复缺陷遵循：

1. Red：写出能稳定复现需求的最小失败测试；
2. Green：实现使测试通过的最小改动；
3. Refactor：在测试保护下拆分职责、消除重复并改善命名；
4. Regression：运行相关测试、全量测试和真实 Windows 构建。

测试应描述用户可观察行为，不绑定私有实现。缺陷测试在修复后长期保留。

## 2. 测试分层

### Dart 单元测试

覆盖：

- JSON 到 Model 的解析和默认值；
- 状态转换、筛选、排序和边界；
- Controller 成功、空、失败和重试；
- 后端地址、主题与偏好处理；
- 不依赖 Flutter 渲染的纯函数。

### Flutter Widget 测试

覆盖：

- 顶层 `NavigationView` 展开与紧凑模式；
- 加载、空、错误和内容状态；
- 表单校验、按钮禁用、对话框确认；
- 主题切换和关键键盘操作；
- 长文本与不同桌面窗口宽度。

测试必须显式提供 `MediaQuery`、主题和依赖，避免依赖开发机隐含环境。

### Python 单元与集成测试

覆盖：

- 应用工厂和 Router 注册；
- API 状态码、校验与错误结构；
- 数据 CRUD、事务和迁移；
- 路径边界、URL 校验与内容解析；
- 任务状态与失败恢复；
- 抓取器使用固定 Fixture 或 Mock，不把不稳定公网当作 CI 前置条件。

### Windows 手工验收

自动化不能替代：

- Release 可执行文件启动；
- 本地后端自动启动并通过健康检查；
- 退出后自有后端关闭；
- 文件选择器、Windows OCR、窗口缩放；
- 亮色/深色、键盘导航和 150%/200% 缩放。

## 3. 强制命令

仓库根目录：

```powershell
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
flutter build windows --release
```

后端目录：

```powershell
Set-Location python-backend
python -m ruff check app tests
python -m pytest
python -m compileall -q app
```

完整发布变更还要执行：

```powershell
./tool/build_windows.ps1
```

## 4. 三轮验证

每项实现至少经过三个层次，而不是机械重复同一命令：

1. 静态轮：格式化、Analyzer、Ruff、依赖与敏感信息扫描；
2. 行为轮：Dart/Python 单元测试和 Widget/接口测试；
3. 产物轮：Windows Release 构建、启动、健康检查和退出。

某轮失败时先修复，再从受影响的最早轮开始重跑。不得把“本地能打开”当作所有测试通过。

## 5. 性能

- 不在 `build` 中解析大 JSON、读文件或发请求。
- 大列表使用惰性构建；稳定 key 避免无意义重建。
- Controller 只通知真正变化的状态。
- 搜索输入使用合适防抖，用户提交操作不重复发送。
- 图片按显示尺寸解码并限制缓存；长章节避免一次创建过多 Widget。
- 后端所有外部请求有超时；下载与翻译并发有上限。
- SQLite 查询避免循环中的重复全表读取。

性能问题必须提供可复现数据：样本规模、硬件、操作、耗时与修改前后对比。

## 6. 完成定义

变更只有同时满足以下条件才算完成：

- 需求与边界明确，未引入手机端或旧技术栈；
- 架构和命名符合规范，无新增巨型文件；
- 正常、空、错误、重试和取消/重复操作已考虑；
- 新行为有测试，旧行为无回归；
- 文档与命令同步；
- 三轮验证通过；
- `git status` 中无缓存、构建产物和无关文件；
- 不包含凭据、数据库、个人数据或受版权保护内容。

## 7. 交付报告

交付说明应简洁列出：

- 已实现的用户结果；
- 关键架构或兼容性决策；
- 实际运行的检查及结果；
- 尚未覆盖的风险或需要用户执行的环境步骤；
- 重要文件的可点击路径。
